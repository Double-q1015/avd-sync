# 爬取策略说明

## 概述

本项目采用**增量+全量**的混合爬取策略，既保证了日常更新的效率，又确保了历史数据的完整性。

## 策略设计

### 1. 增量爬取（Incremental Crawl）

#### 目的
快速获取最新的CVE信息，用于日常更新。

#### 工作原理
1. 从数据库查询最新的CVE发布日期（`publish_date`）
2. 向前回溯N天（默认7天，可配置）作为起始日期
3. 只爬取发布日期大于等于起始日期的CVE
4. 遇到已存在的CVE时，如果信息有更新则自动更新
5. 当页面中所有CVE都早于停止日期时，停止爬取

#### 停止时间确定机制

**初始化阶段**：
```python
# 1. 查询数据库最新CVE发布日期
latest_date = db_storage.get_latest_publish_date()  # 例如: "2024-01-15"

# 2. 向前回溯N天（默认7天）
lookback_days = 7
stop_date = latest_date - timedelta(days=lookback_days)  # 例如: "2024-01-08"
```

**停止条件判断**：
- 只有当**当前页所有CVE**都早于停止日期时才停止
- 避免因单页混合新旧日期而提前停止
- 确保不遗漏任何新数据

**特殊情况处理**：
- **数据库为空**：程序会抛出错误，提示使用全量爬取初始化数据库
- **日期解析失败**：程序会抛出错误，便于发现和修复数据问题

#### 优势
- ⚡ **速度快**: 只爬取新数据，大幅减少爬取时间
- 💰 **资源省**: 减少网络请求和服务器压力
- 🔄 **实时性**: 每日更新，及时获取最新漏洞信息
- 🎯 **智能停止**: 自动判断停止条件，确保数据完整性

#### 适用场景
- 每日自动更新
- 快速获取最新CVE
- 日常监控和维护

### 2. 全量爬取（Full Crawl）

#### 目的
确保历史数据的完整性和准确性，更新已存在的CVE信息。

#### 工作原理
1. 从第一页开始爬取所有数据
2. 直到页面为空（没有更多数据）为止
3. 使用数据库的 `INSERT OR UPDATE` 机制自动更新已存在的CVE
4. 记录全量爬取历史，用于判断下次是否需要全量爬取

#### 优势
- 📊 **数据完整**: 覆盖所有历史数据
- 🔄 **信息更新**: 更新已存在CVE的最新信息
- 🛡️ **数据修复**: 修复可能遗漏或错误的数据

#### 适用场景
- 每月定期全量更新
- 数据修复和验证
- 首次初始化数据库

### 3. 自动模式（Auto Mode）

#### 目的
智能判断执行增量还是全量爬取，无需手动干预。

#### 工作原理
1. 检查数据库中最后一次全量爬取的日期
2. 计算距离当前日期的天数
3. 如果超过配置的间隔天数（默认30天），执行全量爬取
4. 否则执行增量爬取

#### 优势
- 🤖 **自动化**: 无需手动判断
- ⚖️ **平衡**: 自动平衡效率和完整性
- 🔧 **灵活**: 可根据实际情况调整间隔

## 配置说明

### 增量爬取配置

```python
'incremental': {
    'enabled': True,  # 是否启用增量爬取
    'lookback_days': 7,  # 向前回溯天数（防止遗漏）
}
```

**lookback_days 的作用**:
- 防止因为时区、数据延迟等原因遗漏CVE
- 建议设置为3-7天（推荐7天）
- 过大会增加爬取时间，过小可能遗漏数据

**常见问题**：
- **Q: 为什么需要回溯天数？**  
  A: 防止遗漏数据。原因包括时区差异、数据发布延迟、网络延迟、服务器时间不同步等。

- **Q: 回溯天数设置多少合适？**  
  A: 日常使用推荐7天，快速更新可用3-5天，安全优先可用10-14天。

- **Q: 如果数据库为空怎么办？**  
  A: 程序会提示使用全量爬取模式初始化数据库。运行 `python main.py --mode full` 进行初始化。

### 全量爬取配置

```python
'full_crawl': {
    'enabled': True,  # 是否启用全量爬取
    'interval_days': 30,  # 全量爬取间隔（天）
}
```

**interval_days 的建议**:
- 建议设置为30天（每月一次）
- 可根据数据更新频率调整
- 过短会增加服务器压力，过长可能数据不够及时

## 数据更新机制

### INSERT OR UPDATE

数据库使用 `INSERT OR UPDATE` 机制，确保：
- 新CVE：直接插入
- 已存在CVE：如果信息有变化则更新
- 自动去重：基于CVE编号（唯一索引）

### 更新判断

系统会检查以下字段是否有变化：
- title（标题）
- description（描述）
- danger_level（危险级别）
- impact_range（影响范围）
- security_versions（安全版本）
- solution_advice（解决建议）
- reference_links（参考链接）
- exploitability（利用情况）
- package（补丁情况）

## 时间安排建议

### 每日增量爬取
- **时间**: 每天凌晨（如 08:00）
- **频率**: 每日一次
- **耗时**: 通常几分钟到十几分钟

### 每月全量爬取
- **时间**: 每月1号（如 10:00）
- **频率**: 每月一次
- **耗时**: 可能需要1-2小时（取决于数据量）

## 监控和统计

### 爬取统计表（crawl_stats）

记录每次爬取的详细信息：
- 爬取日期
- 总CVE数
- 新增CVE数
- 更新CVE数
- 爬取模式

### 全量爬取历史表（full_crawl_history）

记录全量爬取的历史：
- 爬取日期
- 总CVE数
- 爬取耗时

### 查询示例

```sql
-- 查看最近10次爬取统计
SELECT * FROM crawl_stats ORDER BY crawl_date DESC LIMIT 10;

-- 查看全量爬取历史
SELECT * FROM full_crawl_history ORDER BY crawl_date DESC;

-- 查看增量爬取效率
SELECT 
    crawl_date,
    new_cves,
    updated_cves,
    total_cves
FROM crawl_stats 
WHERE crawl_mode = 'incremental'
ORDER BY crawl_date DESC;
```

## 最佳实践

1. **首次使用**: 执行一次全量爬取初始化数据库
2. **日常维护**: 使用增量爬取每日更新
3. **定期验证**: 每月执行一次全量爬取确保数据完整性
4. **监控统计**: 定期查看爬取统计，了解数据更新情况
5. **调整参数**: 根据实际情况调整回溯天数和间隔天数

## 故障处理

### 增量爬取失败
- 检查网络连接
- 查看日志文件
- 可以手动执行全量爬取作为备选

### 全量爬取超时
- 增加GitHub Actions的timeout时间
- 考虑分批爬取
- 检查服务器响应速度

### 数据不一致
- 执行一次全量爬取修复数据
- 检查爬取日志
- 验证数据库完整性
